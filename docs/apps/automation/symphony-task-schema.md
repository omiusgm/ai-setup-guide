# Symphony: схема задач

!!! info "🤖 Для управления задачами"
    Эта страница нужна, чтобы пользователь и система могли ставить задачи в одном понятном формате, а Symphony мог их распределять без путаницы.

## Зачем это нужно

Если у системы есть только список хотелок, она быстро превращается в шум. Нужны:

- единый формат задачи
- понятные статусы
- критерии готовности
- правила остановки
- механизм подхвата новых задач

## Минимальная схема тикета

Каждая задача должна содержать:

- `id`
- `title`
- `goal`
- `priority`
- `owner`
- `source`
- `status`
- `workspace`
- `checks`
- `ready_for_check`
- `done_criteria`
- `blocked_reason`
- `updated_at`

## Рекомендуемые статусы

- `queued` — задача в очереди
- `assigned` — назначена исполнителю
- `in_progress` — работа идёт
- `blocked` — нужен ответ или зависимость
- `fixing` — идут исправления после проверки
- `ready_for_check` — можно проверять
- `done` — задача завершена
- `failed` — задача не прошла проверки и остановлена
- `archived` — больше не актуальна

## Кто может ставить задачи

### Пользователь

Пользователь может:

- создать новую задачу
- повысить приоритет
- остановить задачу
- добавить уточнение
- перевести задачу в архив

### Система

Система может:

- создать follow-up задачу
- добавить техническую подзадачу
- поставить задачу на проверку
- предложить следующий шаг
- развернуть новую задачу из найденного сигнала

Важно: система не должна молча подменять пользовательскую цель.

### Claude / другой агент

Если Claude или другой агент нашёл полезный следующий шаг, он не должен пытаться "продавить" его напрямую в работу. Вместо этого он:

- пишет запись в [Symphony inbox](symphony-inbox.md)
- указывает `source: claude` или `source: agent`
- кратко объясняет, почему задача полезна сейчас

Так Symphony сможет подхватить задачу в следующем цикле и превратить её в нормальный тикет.

## Источники задач

Задачи могут приходить из:

- пользователя
- системы
- Claude / другого агента
- периодического planner job
- найденных пробелов в документации или workflow

Важно: все источники должны сходиться в одной очереди, а не в разных разрозненных списках.

## Как Symphony берёт задачу

Symphony должен смотреть на:

- приоритет
- блокеры
- готовность к старту
- наличие workspace
- наличие checks

И только потом назначать исполнителя.

## Ready for check

Задача считается готовой к проверке, если:

- код или текст обновлены
- есть лог изменений
- выполнены базовые проверки
- понятно, что именно было сделано

## Done criteria

Задача может попасть в `done`, если:

- все checks прошли
- нет открытых критичных ошибок
- результат можно воспроизвести или проверить
- статус/ссылка/артефакт обновлены

## Stop conditions

Нельзя автоматически закрывать задачу, если:

- checks упали
- неясны критерии готовности
- задача зависит от ответа человека
- есть риск сломать соседние части проекта
- результат ещё не подтверждён

## Follow-up задачи

Symphony может сам создавать новые задачи, если видит:

- пропущенный слой документации
- отсутствующий worker
- необходимость в проверке
- найденный пробел в workflow

Примеры follow-up:

- добавить проверку сборки
- описать шаблон тикета
- создать quality gate
- зафиксировать статусный цикл

## Формат для человека

Когда задача показывается пользователю, лучше коротко:

- что это за задача
- зачем она нужна
- что будет считаться готовым
- что мешает старту
